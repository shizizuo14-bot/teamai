# 项目知识沉淀规则

## 准入条件

仅当一项发现同时满足以下五个条件时，才进行沉淀：

1. **可验证**：有代码、测试、日志、事故记录或已达成共识的记录支持。
2. **持久有效**：在当前任务结束后仍可能持续有用。
3. **可执行**：能明确告诉 Agent 或维护者应该做什么、检查什么。
4. **不重复**：不重复已有指导。
5. **不敏感**：不包含密钥、个人数据或原始凭据。

普通的一次性成功任务不附加知识提案。未经验证的重复问题不作为稳定指导提案。适用的指令链已有等价规则时，不重复提案。这些是负向触发条件，不代表应将最终回复改造成通用的完成报告模板。

## 选择沉淀位置

| 去向 | 适用内容 |
| --- | --- |
| `AGENTS.md` | 稳定、适用面较广的仓库或模块指导。 |
| 独立复盘文档 | 背景、时间线、决策和一次性经验。 |
| 机械检查 | 可由静态检查、测试或脚本强制执行的可重复不变量。 |
| 不沉淀 | 未验证、短期、重复或敏感内容。 |

对已重复发生且经过验证的问题，优先提议最能预防问题复发的去向：简洁规则、机械检查，或两者结合。不得静默创建检查。

## 必需的提案结构

严格使用以下七个部分：

1. **结论**：可长期保留的规则或决策。
2. **证据**：经过验证的来源和位置。
3. **分类**：选择上述一种去向，并说明理由。
4. **目标**：精确的指导文件、其现有章节标题或锚点，以及适用范围；机械检查则写明精确的建议检查范围。
5. **候选文本**：最小、可审查的措辞。
6. **不记录内容**：明确哪些内容刻意不记录。
7. **确认问题**：针对这一具体补丁请求授权。

在全部七个字段中，对检测到的真实或测试凭据统一替换为 `[REDACTED]`，或仅描述为“敏感配置”；任何字段都不得复制凭据原文。

在检查真实目标路径前，**目标** 为 `待审计/待确认`。此时的 **确认问题** 只请求用户提供目标路径并授权只读审计，不得请求写入权限。获得审计授权后，只执行只读发现。审计识别出精确的指导文件、章节或锚点和适用范围后，重新输出完整七段提案，并单独获取明确的写入确认。审计授权永远不作为写入批准。

文档写入确认只授权执行已确认的精确补丁，不授权 Git 暂存、提交、推送或创建 PR；每项版本控制操作都必须由用户另行明确请求或批准。部分确认只适用于指定的候选文本和精确目标章节。新发现的候选项需要新的完整提案和单独确认。

## 拆分文件

将拆分 `AGENTS.md` 始终作为一项提案，不得当作自动清理。列出每个新文件、其作用边界和受影响的现有文件。仅在获得单独明确确认后才可创建或编辑。

## 常见错误

- 将未经验证的结论提升为强约束。
- 将事故时间线或原始证据复制进 `AGENTS.md`。
- 重复其他位置已有的指导。
- 应用知识补丁时覆盖用户改动。
- 将本 Skill 当成自动总结器，而不是提案门禁。

## 示例

三次经过验证的事故表明，SQL `SELECT` 字段行尾的 `--` 注释会吞掉后续 SQL。将时间线压缩为：“`SELECT` 字段列表中禁止使用行尾 `--` 注释；改用独立的 `/* ... */` 注释行。可行时增加静态检查。”附上证据提议规则或检查，等待确认后再修改。
