# 项目知识沉淀

## 核心原则

将经过验证、可复用的发现整理为小而可审查的提案。尤其是某个问题已重复发生，且本次修复已经验证时，即使用户只要求报告任务结果，也应主动建议沉淀对应的防错规则。不要把每个任务都当成文档更新请求。

## 提案前评估

读取[知识沉淀规则](references/knowledge-rules.md)。候选知识必须满足其准入条件；否则说明不沉淀的原因。收集代码、测试、事故或配置证据，并确认适用的指令链中是否已有等价指导。普通的一次性成功任务、未经验证的重复问题或已有等价规则，不附加知识提案。

如果提案涉及 `AGENTS.md` 指令链，对用户的实际目标运行 `scripts/inspect_agents.py <用户目标路径>`，识别文件、作用范围和 Git 状态。在只读审计成功前，将 **目标** 设为 `待审计/待确认`；不得根据当前工作目录或本 Skill 仓库猜测目标。只读审计授权不等于写入授权。提案不涉及 `AGENTS.md` 时，不运行此脚本。

## 提案契约

按参考规则固定输出七个部分：结论、证据、分类、目标、候选文本、不记录内容、确认问题。可供确认的写入提案中，**目标** 必须包含精确的指导文件、现有章节标题或锚点，以及适用范围（例如仓库、模块或路径）。只读审计找到目标后，重新输出包含这三项信息的完整七段提案；不得把审计授权当成写入确认。对已重复发生且本次已验证的问题，仅在确有沉淀价值时提供简洁提案；该提案是建议，不是通用的完成报告模板，也不代表已经修改文件。

## 确认门禁与补丁

在用户明确确认当前提案前，不得创建、拆分、覆盖或编辑知识文件。文档写入确认只授权执行已确认的精确补丁，不授权 Git 暂存、提交、推送或创建 PR；每项版本控制操作都必须由用户另行明确请求或批准。部分确认只适用于指定的候选文本和精确目标章节。如果审计又发现了新候选项，重新输出完整提案并等待单独确认。获得确认后，使用最小范围补丁，保留用户的无关改动。再次检查选定目标，避免重复已有指导。

## 验证

验证结果准确、可执行、不含敏感信息、位置正确，且严格限于已确认范围。运行相关机械检查，并报告所用证据。
